# Spike 结果 —— 四条架构假设的实测验证

- 日期：2026-09-11
- 环境：Windows 11 Pro for Workstations 26200 · CPython 3.12.10 · `windows-capture` 2.0.1
- 机器：主显示器 **3440×1440**，系统缩放 **125%**
- 结论：**四条假设全部成立**，架构无需修改。另发现 5 条实现级陷阱，已列入下方「实现必读」。

---

## 总览

| # | 假设 | 结论 | 证据 |
|---|---|---|---|
| S1 | `windows-capture` 能按 HWND 截被遮挡窗口 | ✅ **成立** | 截到完全被遮挡的目标窗自身内容（品红），肉眼可验 |
| S2 | ctypes 能实现覆盖层（分层窗口 + 逐像素 alpha + 点击穿透 + 置顶） | ✅ **成立** | 截图里能看到青色光晕带，控制组有效 |
| S2b | `WDA_EXCLUDEFROMCAPTURE` 能让覆盖层从截图消失 | ✅ **成立，且对 DXGI 也生效** | A/B/C 三组对照全部通过（Q-017 解决） |
| S3 | ctypes 低级钩子能区分物理/注入事件，且能拦截 | ✅ **成立** | 注入事件标志准确；拦截模式下应用收不到输入 |
| S4 | ctypes 手写 SDDL 的管道 DACL 真被内核执行 | ✅ **成立** | 证伪组「只授权 SYSTEM」时当前用户被拒（err=5） |

## S1 —— 截图能力

```
[PASS] Q1a/Q1b 按 HWND 截被遮挡窗口
       hwnd=0x670B38 mean_rgb=(255,28,255) 距离: 期望=28 干扰=400 -> 期望色
[PASS] Q1c DXGI Desktop Duplication   3440x1440
[PASS] Q1a' 按显示器截全屏            3440x1440
```

**关键结论：WGC 窗口捕获不受遮挡影响。** 目标窗被一个绿色窗口完全覆盖，截出来的仍是目标窗自身的
品红内容（含标题栏）。这是主截图路径（DEC-007 第 1 层）成立的直接证据。

**派生的实现事实**：截出的图**包含标题栏**，即图像 `(0,0)` 精确对应 `GetWindowRect()` 的 `(left, top)`。
点击映射为 `screen = (left + x, top + y)`，无偏移 —— 直接支撑 CONSTRAINT-003（截图与坐标同源）。

## S2 / S2b —— 覆盖层与截图排除

```
S2（WGC 路径）
[PASS] A 基线（无覆盖层）        边缘 BGR=(46,70,22)   见青色=False
[PASS] B 控制组（覆盖层，无 WDA） 边缘 BGR=(218,221,4)  见青色=True
[PASS] C 覆盖层 + WDA（WGC）     边缘 BGR=(42,62,21)   见青色=False

S2b（DXGI 路径，三组对照）
[PASS] C1 DXGI 无覆盖层          非黑帧 3440x1440
[PASS] C2 DXGI + 覆盖层，无 WDA   边缘 BGR=(218,221,4)  见青色=True
[PASS] C3 DXGI + 覆盖层 + WDA     边缘 BGR=(42,62,21)   见青色=False -> WDA 对 DXGI 同样生效
```

**B / C2 是控制组**，它们证明覆盖层确实画在屏幕上、且两种捕获路径确实看得见它。
没有它们，C / C3 的「没有青色」无法区分「WDA 生效」和「覆盖层压根没显示」。

**Q-017 就此解决**：官方文档未明确 DXGI 是否遵守 WDA，且有来源称部分 GPU/驱动组合会绕过。
**本机实测：不绕过。** 覆盖层不会污染任何截图路径。
（注意：这是本机 GPU/驱动的实测结论，换机器理论上需复验；主路径 WGC 已由 C 组确认。）

## S3 —— 输入钩子

```
[PASS] P0 对照（无钩子）           SendInput 成功=True  Entry='abc'
[PASS] Q3a 低级钩子安装            键盘钩子=True 鼠标钩子=True  err=0
[PASS] Q3b 注入标志识别            键盘事件 注入=6 物理=0；鼠标事件 注入=1
[PASS] P1 放行模式下应用收到输入    Entry='abc'
[PASS] Q3c 钩子能拦下注入事件       Entry=''（应为空）
```

**Q3b 是本项目的安全核心**：钩子能准确读出 `LLKHF_INJECTED` / `LLMHF_INJECTED`。
这正是「AI 的 `SendInput` 放行、用户的物理输入被吞」这条机制的支点。

**Q3c 证明拦截是真的**：拦截模式下 `SendInput` 的三个字符没有到达应用（Entry 为空）。

**顺带验证**：`SendInput` 的 `KEYEVENTF_UNICODE` 路径可用（测试字符正是走这条路送达的），
即生产环境中中文输入的方案可行。

**测试的安全设计**：本 spike 的拦截模式刻意与生产逻辑相反（**吞注入、放行物理**），
因此它**不可能影响用户的真实键鼠**；另配 15 秒看门狗强制卸载。

### 未验证的一小半（诚实标注）

「物理事件的 INJECTED 标志为 0」这一侧**没有实测** —— 测试期间没有人按下物理按键
（日志里 `物理=0` 正是因为没有物理输入）。它依据的是该标志的文档语义与注入侧的实测补集。
风险极低（同一个结构体字段），5 秒即可确认：在 S3 运行期间手按任意键，看是否出现 `物理=1`。

## S4 —— 命名管道 ACL

```
当前用户 SID = S-1-5-21-...-1001
[PASS] T1 授权 当前用户+SYSTEM    可连接=True  err=0
[PASS] T2 只授权 SYSTEM（证伪组）  可连接=False err=5  -> DACL 被内核执行
[PASS] T3 授权 Everyone（对照组）  可连接=True  err=0
```

**证伪设计**：证明「其他用户连不上」本需要第二个账户。改为建一条**不授权当前用户**的管道 ——
若当前用户连它也被拒（`ERROR_ACCESS_DENIED=5`），说明 DACL 确实被内核执行，那么
「只授权当前用户」的那条自然对其他用户生效。T3 是配套对照，排除「失败是因为别的原因」。

**结论：不引入 pywin32 是可行的。** DEC-036 成立。

## 实现必读 —— 本次 spike 踩到的 5 个陷阱

1. **DPI 声明是硬前提，且效果可量化。**
   不声明 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` 时，
   `SM_CXSCREEN` 返回 **2752**；声明后返回 **3440**。差 25%（=125% 缩放）。
   **所有坐标读取之前必须先声明**，否则每次点击都偏 1/4 屏。

2. **ctypes 的 `restype` 不声明就按 32 位 int 处理，会截断句柄。**
   `GetCurrentProcess()` 返回伪句柄 `(HANDLE)-1`，被截断成 `0xFFFFFFFF` 后，
   `OpenProcessToken` 报 `ERROR_INVALID_HANDLE(6)`。**所有返回句柄的 API 必须声明 `restype`。**
   这正是 DEC-034 预判的易错点，第一次运行就命中了。

3. **WGC 的 `Frame` 与 DXGI 的 frame 不是一个类型。**
   WGC `Frame` 有 `save_as_image()` / `convert_to_bgr()` / `frame_buffer`，**没有** `to_bgr()`；
   `to_bgr()` 属于 DXGI 的 frame。调错方法得到的报错是 `AttributeError`，不提示该用哪个。

4. **DXGI 需要循环取帧预热。**
   新建 `DxgiDuplicationSession` 后立刻取帧，可能拿到**整帧全黑**（实测发生过：
   `mean=0.0 max=0`）。必须循环取若干帧并丢弃全黑帧，必要时重建会话。

5. **低级钩子必须在有消息循环的线程上安装，且回调必须持有引用。**
   钩子回调是 `WINFUNCTYPE` 对象，被 GC 回收后系统会调用野指针 —— 必须保存在实例属性上。

## 遗留与后续

- **独占全屏场景未验证**（S1 未构造该场景）。WGC 截不到独占全屏是微软官方结论，
  兜底走 DXGI DD 已由 S1c 证明可用；但「DXGI 能否截独占全屏」本身仍未实测。
- **WGC 黄框**：`draw_border=False` 已传，S1 的截图中未见黄框 —— 初步有效，未见边界情形。
- **多显示器未验证**（本机单显示器）。
- **本 spike 代码是一次性的**（`spike/`），不是产品代码。其中 S2 的覆盖层绘制、
  S3 的钩子线程、S4 的 SDDL 构造是产品实现的原型，可作参考起点。
